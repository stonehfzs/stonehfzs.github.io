## 0. 背景

在阿里云 ECS 上使用 Overleaf Toolkit 部署社区版后，计划使用 Nginx 作为反向代理，同时支持 Web 端与 VS Code 的 `Overleaf-Workshop` 插件进行远程编辑。

但在配置过程中遇到了若干典型问题：

1. 本地系统服务占用常用端口，导致 Overleaf 容器端口冲突。
2. Certbot 自动生成的强制 HTTPS 跳转（`301 Moved Permanently`）导致 VS Code 插件解析崩溃，陷入无限报错死循环。
3. Nginx 默认站点抢占 80 端口，导致请求未穿透到后端服务，直接返回系统默认的 404 HTML 页面。

以下记录完整的排查与修复流程。

---

## 1. 解决端口冲突与 Overleaf 端口迁移

Toolkit 默认可能会占用 80 或 8080 端口。在部署了 CrowdSec 或其他安全防护工具的服务器上，`127.0.0.1:8080` 常被占用，导致容器端口绑定失败。

### 检查端口占用

```bash
ss -tlnp | grep :8080

```

如果输出显示 `crowdsec` 正在监听，建议将 Overleaf 的外部暴露端口修改为一个干净无占用的端口（如 `8088`），避免与系统服务冲突。

### 修改 Overleaf Toolkit 端口

编辑 Toolkit 配置文件：

```bash
# 修改 config/overleaf.rc
vim config/overleaf.rc

```

修改以下两项：

```bash
OVERLEAF_PORT=8088
SIBLING_CONTAINERS_ENABLED=false

```

重启容器生效：

```bash
bin/stop
bin/up -d

```

确认容器运行状态：

```bash
docker ps -a

```

确保 `sharelatex` 容器状态为 `Up`，且映射为 `0.0.0.0:8088->80/tcp`。

---

## 2. 清理系统级 Nginx 默认站点干扰

CentOS / Alibaba Cloud Linux 自带的 Nginx 默认配置会在 80 端口挂载一个全局站点，返回带有系统样式的 404 页面，必须手动清理。

### 排查默认 server 块

```bash
grep -n "server {" /etc/nginx/nginx.conf

```

### 注释默认配置

编辑 `/etc/nginx/nginx.conf`：

```bash
vim /etc/nginx/nginx.conf

```

找到第 37 行附近的默认 `server { ... }` 块并全部注释：

```nginx
#    server {
#        listen       80 default_server;
#        listen       [::]:80 default_server;
#        server_name  _;
#        root         /usr/share/nginx/html;
#
#        # Load configuration files for the default server block.
#        include /etc/nginx/default.d/*.conf;
#
#        error_page 404 /404.html;
#        location = /404.html {
#        }
#    }

```

同时确认该文件中 `http { ... }` 内部保留了引入外部配置的语句：

```nginx
include /etc/nginx/conf.d/*.conf;

```

## 3. 解决 301 重定向与 VS Code 插件崩溃问题

`Overleaf-Workshop` 插件底层使用 Node 请求库，无法自动处理针对 API 的 `301 Moved Permanently` 响应。当 Nginx 配置了 HTTP 强制跳转 HTTPS 时，插件收到了 Nginx 吐出的 HTML 代码，导致 JSON 解析崩溃，报错残留在工作区。

为兼顾兼容性，最佳方案是：**同一个 server 块内同时监听 80 和 443 端口，双协议直通，不设任何强制跳转规则**。

### 编写反向代理配置

将配置写入 `/etc/nginx/conf.d/overleaf.conf`（将 `hefengzhishui.top` 替换为你自己的域名）：

```nginx
server {
    listen 80;
    listen 443 ssl;
    server_name hefengzhishui.top;

    client_max_body_size 100M;

    # SSL 证书配置（由 Certbot 或手动申请）
    ssl_certificate /etc/letsencrypt/live/hefengzhishui.top/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/hefengzhishui.top/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    location / {
        proxy_pass [http://127.0.0.1:8088](http://127.0.0.1:8088);
        proxy_http_version 1.1;

        # WebSocket 长连接支持
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 防止心跳超时断开
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}

```

> **注意**：绝对不要在配置中添加 `return 301 https://$host$request_uri;` 或 `return 404;`，否则会导致插件和外部 API 请求异常。

## 4. 服务生效与网络验证

### 测试并重启服务

```bash
# 测试配置文件语法
nginx -t

# 重启 Nginx
systemctl restart nginx

```

### 验证端口监听

检查 Nginx 是否同时监听了 80 和 443：

```bash
ss -tlnp | grep nginx

```

正常输出应包含两行，分别绑定了 `:80` 与 `:443`。

### 本地网络连通性测试

在服务器终端直接发起 HTTP 请求：

```bash
curl -I [http://127.0.0.1](http://127.0.0.1)

```

**预期输出**：
返回 `HTTP/1.1 302 Found` 并且 `Location: /login`，同时携带 `Set-Cookie: overleaf.sid=...`，说明反向代理已成功穿透到 Overleaf 容器。
